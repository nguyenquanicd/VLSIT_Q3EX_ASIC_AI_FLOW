# VLSIT_Q3EX_ASIC_AI_FLOW

Example designs that were generated by the **Q3TUI** and **Q3CORE** ASIC AI Design flow. Each example is the complete
output of one run: the hand-written intent, the specification, the RTL, the testbench, the firmware, the constraints,
the reports and the questions the flow asked while it worked. The examples show what the flow produces and where its
results still need a person.

## Examples

| Example | What it is |
|---|---|
| [`rv32iv/`](rv32iv/) | A processor that executes the open **RISC-V** instruction set (RV32I base with multiplication, 5-stage pipeline) plus an in-house **vector unit** (a subset of the RISC-V Vector extension, Zve32x, 128-bit registers, 4 lanes). With two memories, a control/status register block and a UART it forms a small system-on-chip. Application: recognizing a handwritten digit (MNIST) with an INT8 neural network. Specification → RTL → verification → FPGA (Intel Arria 10, 200 MHz), generated by Q3TUI from one intent document |

The README of each example explains its design in detail, describes the instruction set it implements (every instruction,
with its meaning and an example), lists what it can be used for, and has its own glossary.

## Glossary of the terms used in this file

| Term | Meaning |
|---|---|
| **ASIC** (application-specific integrated circuit) | A custom chip. The flow targets ASIC design; the examples are also prototyped on an FPGA |
| **FPGA** (field-programmable gate array) | A re-programmable chip used to test a design before making a custom chip. **Intel Arria 10** is the FPGA family used here |
| **AI flow, agent** | A design flow in which AI programs (*agents*) do the steps: write the specification, write the code, run tests and fix failures |
| **Q3TUI, Q3CORE** | The AI design flow (Q3TUI is its terminal user interface with several agents, Q3CORE the engine behind it) that produced the examples |
| **VLSIT** | The organization name used in file headers and rule names (for example `VLSIT - Q3TUI` as the author of generated files) |
| **Intent** | The one document written by a person that tells the flow the goal and the constraints |
| **Spec** (specification) | The detailed description of the design, with numbered requirements (`REQ-nnn`), written by the flow from the intent |
| **RTL** (register-transfer level) | The hardware description in SystemVerilog (`.sv` files) from which a chip or FPGA is built |
| **Testbench** | The program that drives the design in simulation and checks its answers |
| **Firmware** | The program that runs on the processor of the design |
| **SDC** (Synopsys Design Constraints) | A file that gives the clock and the input/output timing to the synthesis and timing tools |
| **Synthesis** | Turning RTL into gates (or FPGA cells). The examples report results *after synthesis*; place-and-route is a later step |
| **Simulation** | Running the design on a computer with a hardware simulator (VCS, Verilator) to see whether it is correct |
| **Lint** | Automatic checking of code for mistakes and rule violations |
| **Golden model** | A trusted program (here in Python) that computes the exact expected result for comparison, bit by bit |
| **Review gate** | A point where a person would approve a result before the flow continues; in these runs it was approved automatically |
| **Triage** | Finding the cause of a failure and deciding what to fix |
| **CSR block** | A block of control/status registers that software reads and writes at memory addresses (generated by the APB-CSR-Generator tool) |
| **UART** | A serial port (universal asynchronous receiver/transmitter) |
| **MNIST** | A public set of handwritten-digit images (28 × 28 pixels, digits 0 to 9) used to test classifiers |
| **INT8** | A signed 8-bit integer (−128 to 127), used to store the weights and values of a small neural network |

## What an example folder contains

| Folder or file | Content |
|---|---|
| `README.md` | Origin, method, design, instruction set, applications, results and limits of the example |
| `spec/intent.md` | The only human input: goal, scope and constraints in one document |
| `spec/spec.md` | The specification the flow wrote from the intent (the VLSIT template, numbered requirements) |
| `src/rtl/`, `src/tb/`, `src/sw/` | RTL, testbench and firmware |
| `constraints/` | SDC for the FPGA and sanity flows |
| `schemas/` | Structured spec, configuration, test plan, simulation and FPGA evidence, and `questions/` with every question the flow asked and how it was settled |
| `reports/`, `reviews/` | Test results and review records |
| `config/tools.json`, `q3tui.yaml` | The tools by role and the project settings of the run |

The internal state of the flow (`.q3tui/`) and the tool output (`build/`) are not included. Install paths and license
servers were removed.

## How to read an example

1. Read the example's own README: glossary, origin, method, hardware, instruction set, applications, results and limits.
2. Compare `spec/intent.md` with `spec/spec.md` to see what the flow added to a short human description.
3. Read `schemas/questions/` to see which gaps the flow found in its own specification and which defaults it chose.
4. Look at `reports/` and `schemas/` for the evidence, and at the limits section of the README for what the evidence does not show.

## Notes on the evidence

- The flows ran with the review gates approved automatically and the open questions answered with the defaults the flow
  proposed, so the decisions in these examples were not reviewed by a person.
- Results are those reported by the flow. The reports in each example say whether a result is a simulation, a synthesis
  or a measurement, and which data were synthetic (the `rv32iv` network uses placeholder weights and images, so its tests
  check bit-exact agreement with the golden model, not recognition accuracy).
- File headers name `VLSIT - Q3TUI` as the author of generated files.
