# Closed

- **Q-R1** The spec names the module's output only as 'internal reset' and gives no port name. I used `o_rst_n_core`. Is that acceptable for m_soc_top wiring? → Output port is o_rst_n_core; PARA_VLEN and PARA_LANE_COUNT are not used by this module and are not declared. _(default accepted)_
- **Q-R2** RST-04 asks for a test-mode reset override in a wrapper or reset controller. The spec defines no DFT ports, so none was added. Is that acceptable? → No DFT scan reset-bypass port is added (spec lists none). _(default accepted)_
- **Q-R4** The spec gives no port list for m_pc_gen. I assumed inputs i_stall, i_redirect_taken, i_redirect_addr[31:0], i_illegal, i_ebreak and outputs o_pc, o_halt, o_err_illegal. Should m_pc_gen own the halt flags (o_halt / o_err_illegal) and the PC, or should the halt flags live elsewhere in m_cpu_top? → m_pc_gen owns the PC and the sticky halt flags. m_cpu_top connects o_pc to o_imem_addr and the halt flags to the top-level o_halt / o_err_illegal. It also uses o_halt to squash younger IF/ID/ID-EX instructions and to stop the illegal or ebreak instruction itself from executing. _(default accepted)_
- **Q-R5** When i_stall and i_redirect_taken are both 1, which wins? I let the stall win, so a branch held in EX re-presents its redirect when the stall ends. The same rule keeps halt commit off while stalled. → Stall has priority over redirect and over halt commit. m_hazard_unit must not stall the PC in the same cycle that a taken branch in EX must redirect, or must hold the branch in EX. _(default accepted)_
- **Q-R6** The spec gives no port list for m_imm_gen. Should it take only the instruction word and select the immediate format from the opcode itself, or take an immediate-format select from m_cpu_dec? → Ports are i_instr[31:0] and o_imm[31:0]. The format is decoded from the opcode inside the module, so m_cpu_dec does not need to drive a select. _(default accepted)_
- **Q-R8** The spec does not define the m_alu port list or op encoding. Should the ALU interface be i_op_a, i_op_b, a 4-bit i_alu_op and o_result? That also means m_cpu_dec and m_id_ex_reg must use the same ENUM_ALU_OP_* codes, and the operand muxing for pc/imm lives outside m_alu. → Ports are i_op_a, i_op_b, i_alu_op[3:0] and o_result. Op codes are ADD=0, SUB=1, SLL=2, SLT=3, SLTU=4, XOR=5, SRL=6, SRA=7, OR=8, AND=9, PASS_B=10. Operand selection happens upstream of m_alu. _(default accepted)_
- **Q-R9** The spec does not define the decode-to-EX control interface (the signals m_cpu_dec sends through ID/EX), so I defined one: alu_op[3:0], alu_a_pc_sel, alu_b_imm_sel, funct3[2:0], wb_sel[1:0], is_branch/is_jal/is_jalr/is_mul/is_vec, mem_rd, mem_wr, rf_we, plus pc, instr, rs1/rs2 data, imm and rs1/rs2/rd indices. Does m_cpu_dec (and the other EX-side modules) agree with this set and these widths? → Use the interface exactly as written in the file; m_cpu_dec, m_alu, m_branch_unit, m_mul and m_hazard_unit connect to these names and widths. _(default accepted)_
- **Q-R10** How does the load-use bubble reach this register? I assumed the hazard unit drives i_flush for both a taken branch/jump and the load-use bubble, and drives i_stall for the vector stall, with flush taking priority over stall. → i_flush covers both a taken branch/jump and the load-use bubble; i_stall is the vector stall; flush has priority over stall, as in m_if_id_reg. _(default accepted)_
- **Q-R11** The spec gives no port list for m_branch_unit. I defined: inputs i_branch, i_jal, i_jalr, i_funct3, i_rs1_data, i_rs2_data, i_pc, i_imm; outputs o_taken, o_target, o_link_data. Is this interface acceptable, in particular that m_branch_unit also produces the jal/jalr link address (PC+4)? → Interface as defined. m_cpu_top and m_id_ex_reg connect to it, and the link value is muxed into the EX result by the parent or m_alu. _(default accepted)_
- **Q-R12** The task assigns REQ-002, while spec.md names this requirement REQ-FUNC-002. Should the file tag use REQ-002 or REQ-FUNC-002? → Tagged REQ-002, exactly as assigned in the task. _(default accepted)_
- **Q-R13** The spec does not define the m_ex_mem_reg port list. Shall the EX/MEM register carry the pc_plus4 link value, the store data (forwarded rs2) and the wb_sel, with the ALU/MUL/vector-vl result muxed before the register into one i_alu_result? → Ports: i_alu_result, i_store_data, i_pc_plus4, i_rd_idx, i_funct3, i_wb_sel, i_mem_rd, i_mem_wr, i_rf_we, i_valid, i_stall. - **Q-R14** What are the wb_sel encodings produced by m_cpu_dec? The spec does not define them, and m_cpu_dec does not exist yet. → 00 = ALU result, 01 = load data, 10 = PC+4, 11 = recovers to ALU result _(default accepted)_
- **Q-R15** Where does the write-back mux live? m_cpu_top is structural (HIE-02) and the spec lists no separate WB module, so I put the mux inside m_mem_wb_reg and expose o_wb_data. → The write-back mux is inside m_mem_wb_reg. _(default accepted)_
- **Q-R16** How should the stage behave during MEM stalls (MMIO/APB wait) versus the vector stall? I assumed i_stall holds the stage (the repeated register-file write is idempotent) and i_flush inserts a bubble. For a pending MMIO access in MEM, m_cpu_top should drive i_flush so the unfinished instruction does not advance. → i_stall holds the stage; i_flush inserts a bubble and has priority over i_stall. _(default accepted)_
